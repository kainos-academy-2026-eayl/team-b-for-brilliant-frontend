Frontend does not mean “everything runs in the browser”. In this app, much of the frontend runs on a server. That server is a server to the browser, but a client when it asks the backend for data.

Read: MDN's client-server primer. HTTP clients are programs that send requests; they need not be browsers. HTTP roles.

2. Two requests, two kinds of response

An HTTP request is a message asking a server to do something. GET asks to retrieve something. A response is the server's reply, with a status such as 200 for success and a body containing the result.

Browser → frontend: GET http://localhost:8000/products
Frontend → backend: GET {API_BASE_URL}/products

Backend → frontend: JSON product data
Frontend → browser: HTML product page

Port 8000 is an example frontend address. The backend address comes from configuration; the product service defaults to port 3001 if API_BASE_URL is absent.

JSON is a text format for transferring data. HTML describes page content. They are not interchangeable.

JSON data, shortened:
{"products":[{"name":"Travel bag"}]}

HTML page fragment:
<h2>Travel bag</h2>

The JSON above is an illustration, not a complete response accepted by this app's schema.

Sources: HTTP overview and JSON.

3. Follow the actual product-list request

  1. Enter the frontend. src/app.ts configures Express. Matching middleware runs first: it can prepare request/session information, continue the request or stop it. The /products route is mounted here. Middleware reference.
  2. Choose the handler. controllers/products.ts handles the incoming GET. Its fetchProducts() parameter is normally wired to getProductsWithPrices by app.ts. This is a function call inside the frontend process, not another HTTP request.
  3. Ask the backend. services/products.ts calls fetch for the backend's /products. response.json() turns the JSON response body into JavaScript values. await waits for the operation's result before the next line uses it. Node.js fetch reference.
  4. Check and prepare the data. The product service uses ProductsResponseSchema.safeParse to check the actual values. It keeps visible products, rewrites image URLs through the frontend, sorts images by imageOrder and obtains each current price. Zod validation reference.
  5. Build the page. The controller calls res.render('products/index.njk', { products }). Nunjucks combines the product template, the shared layout and the prepared data to produce HTML. The browser receives that HTML. This is server-side rendering. Nunjucks rendering reference.
The data path to remember:
backend JSON → JavaScript values → schema check → prepared products → template → HTML.

The browser then makes additional requests for CSS, scripts and images referenced by that HTML. The menu script is one of those browser-side assets; it does not fetch the catalogue. How browsers load page resources.

One important distinction: models versus schemas

The product model is a TypeScript interface describing the expected shape while writing/checking code. It does not inspect a backend response while the app runs.

The product schema is executable Zod validation. It checks real incoming values at runtime. JSON can be syntactically valid yet fail that schema, for example if imageOrder is a string instead of the required integer.

TypeScript: erased types · Zod: parsing data.

Where does this responsibility live?

A map of this application, not a rule that every application must use the same folder names.

The product-list path

Browser GET /products
  → app.ts: middleware and router wiring
  → controllers/products.ts: incoming HTTP handler
  → services/products.ts: outgoing backend fetch
  ← backend JSON
  → schemas/product.ts: runtime shape check
  → services: filter visibility, proxy/sort images, fetch prices
  → controller: res.render(..., { products })
  → views/products/index.njk + views/main.njk: HTML
  ← browser displays HTML, then requests assets

The arrows between frontend folders are ordinary function/data flow, not HTTP between folders. Only the browser/server and frontend/backend boundaries shown above involve HTTP.

Framework background: MDN client-server overview, Node fetch and Nunjucks rendering.

The eight folders you asked about

clients/

Job: speak the protocol of a particular external API.

accountClient.ts sends credential and MFA requests to the account service and interprets its responses. Here, “client” means an HTTP-calling component, not the browser or a customer.

Boundary: it does not render HTML. Product services currently call fetch directly; product requests do not pass through this folder.

controllers/

Job: handle an incoming HTTP request and choose its response.

products.ts calls a product-fetching function, renders a template, or returns an error page/status. This repository also defines Express routers in these files; it has no separate routes folder.

Clue: req, res, res.status, res.render.

middleware/

Job: apply request-wide or route-specific checks before passing control on.

csrf.ts prepares a session token and rejects POSTs with an invalid token. requireAuth.ts protects the account route, not every product route.

Clue: next() continues the chain; a response/redirect can stop it. Express reference.

models/

Job here: describe application data shapes to TypeScript.

product.ts declares interfaces such as Product, ProductImage and ProductWithPrice. They aid autocomplete and static checking.

Not: a database connection or executable validator. These interfaces are erased from the JavaScript. TypeScript reference.

schemas/

Job: check actual external data when the application runs.

product.ts uses Zod to require the expected fields and types, including a non-negative integer imageOrder. The service calls safeParse on decoded JSON.

Not: SQL tables or database migrations. Valid JSON can still be invalid product data. Zod reference.

services/

Job: retrieve and prepare data and apply application rules.

products.ts fetches products, checks schemas, filters hidden products, rewrites/sorts images and obtains prices. authService.ts applies sign-in/MFA rules using the account client.

Boundary: services return data to controllers; they do not call res.render.

types/

Job here: extend library type declarations for this application.

express-session.d.ts tells TypeScript the session can contain customerId, csrfToken and pending MFA details.

Not: code that creates or saves a session. The session middleware does that at runtime. Both this folder and models/ contain type information; their separation is organisational.

utils/

Job: small reusable helpers, not whole page flows.

concurrency.ts limits how many asynchronous jobs run at once. Product services use it when fetching prices. safeRedirect.ts accepts local redirect paths or uses a fallback.

Boundary: neither helper decides which HTML page to render.

The academy MVC slides explain the general separation of responsibilities. Their class-based examples differ from this project's function/router factories. The models/DTOs slides discuss richer domain classes; this project's product models are plain interfaces.

Three supporting locations

  • src/index.ts: loads environment configuration and starts the listening server. src/app.ts: configures middleware, templates and routes.
  • views/: Nunjucks templates executed on the frontend server. main.njk supplies the common layout; product templates supply page content.
  • public/: browser assets. For example, menu.js changes the drawer in the browser; it does not fetch products. Public assets are mounted at /static.
Not every route visits every folder. Product retrieval uses product services directly. Sign-in uses a controller, an auth service and the account client. Models and type declarations are development-time descriptions, not extra runtime “stations” through which a request travels.

In this repository, the product route is server-rendered. Do not generalise that to every feature: the intended registration/verification browser scripts make their own API requests. The earlier review found their served-script wiring needs separate repair; these lessons do not change application behavior.

What happens to retrieved product information?

Data handling in the checked-out product implementation
StageWhat happens
HTTP resultresponse.ok checks for a successful HTTP status before parsing.
Decoderesponse.json() converts JSON text into JavaScript values. It does not prove they are valid products.
ValidateZod checks expected data fields/types. A schema failure throws; it is not treated as an empty catalogue.
PrepareInvisible products are removed. Valid backend image URLs are rewritten to frontend image routes, images are ordered and prices are attached.
RenderThe controller passes prepared data to Nunjucks. The template produces the browser's HTML response.
FailureA failed catalogue lookup produces a 502 error page. A missing/hidden selected product produces 404. A price lookup failure is logged and leaves the product visible with “Price unavailable”.

The product-fetching code does not write these products to a frontend database. It prepares data for a response. Backend storage is a separate responsibility.

Implementation: product service, price service, product controller and product schemas.

Where would I look first?

  • “Products response ... did not match schema”: compare actual backend JSON with schemas/product.ts. A model interface alone cannot repair a mismatched response.
  • “Failed to fetch products: HTTP 500”: the frontend received an error status from the backend. Check the backend response/logs as well as the frontend service.
  • Correct data, wrong page markup: check controller-to-template data and the product templates.
  • Menu fails to open: check the browser-side menu script and served asset, not the product API.

These are starting points, not guarantees about the cause. Read the observed error and follow its data path.
